# Learnings

Short, dated observations that haven't earned a topical rule yet.

- [2026-04-19] When renaming salience map keys (e.g., the unified `conversation.user.text` migration), the host-bind-mounted yaml at `~/.sentient/gateway/config/salience_map.yaml` must be edited in place before restarting the gateway container. The repo's `gateway/salience_map.yaml` is the template for fresh setup runs, not the live config — the container reads its mount target at startup and never re-syncs. Drift between the two manifests as silent empty salience lookups (`salience-lookup-empty` DEBUG), cycles never firing.
- [2026-04-20] `<system-reminder>` XML wrapped inside `role: "user"` content is a Claude/Anthropic convention. OpenAI models (gpt-4.1-mini, gpt-4o, etc.) treat it as plain user content with user-level authority — lower than system. For OpenAI / OpenRouter ephemeral per-turn context, use a separate `role: "system"` (or `role: "developer"` on newer models) message, NOT XML inside a user message.
- [2026-04-20] Optimistic-pending UI dedup keyed on text alone fails when the same text is sent twice. The OLD `buildHistoryTextMap` mapped `text → earliest ts`; once "hi" had a server echo, every subsequent "hi" had `serverTs < createdAtMs` and stayed stuck pending forever. Fix: per-text **FIFO array** of server timestamps; each pending claims one unmatched echo (`cycle-helpers.ts:reconcilePending`). **Update (this branch):** the cleaner fix shipped — `pendingId` is now an optional field on `text.input` + the user conversation-feed item (`shared/protocol`), threaded onto the committed user echo by the gateway, so the client reconciles by exact id. The text-FIFO path remains the fallback when `pendingId` is absent (legacy clients).
- [2026-04-20] Logtape's default file sink truncates long string fields at ~180 chars (the `…"` suffix in dumps). Burned ~30 minutes chasing the wrong root cause when an `assembled-message` debug log silently truncated the system message we needed to inspect. Either keep debug content fields short, or write the full payload to a separate file (e.g., `/tmp/last-llm-request.json`) for inspection.
- [2026-04-20] Rule of thumb for any OpenAI / agentic-workflow design decision: consult OpenAI's official docs, API reference, and the Cookbook FIRST. Claude's training data lags actual model/API behavior and is biased toward Anthropic conventions (e.g. `<system-reminder>` XML, `developer` vs `system` role semantics, tool-call round-trip shape, prompt-caching rules). When unsure, fetch current docs via `context7` MCP or web fetch — do not let Claude's prior-assumption stand in for verified behavior.
- [2026-06-05] Mobile streaming cadence (clean-arch refactor Phase 0): gateway delta cadence = **INCREMENTAL**. The gateway emits one `message.delta` per Hermes `text.delta` chunk, sent straight to `ws.send` with no buffering on the SDK-facing path — `hermes-event-translator.ts:208` inside the `for await (const ev of events)` loop (`:90`), `emit` bound directly to `ws.send` at `ws-session-configure.ts:128`. UtteranceAggregator batches only the TTS fork (`textDeltas`), not the client/translator stream. ⇒ The mobile "whole assistant message + task pills pop in at once" bug is purely **client-side `StateFlow<SdkState>` conflation** (a burst of deltas collapses to one collected frame), NOT a gateway batching issue. Fix is the SDK's no-loss `events: SharedFlow` surface; no gateway-pacing change needed. Determined statically from gateway source (no runtime trace required).
- [2026-05-08] ACP pivot: sentient is no longer a Hermes platform — it is an ACP client. Per-profile transport is `acp_ws_server.py` wrapping `hermes -p <profile> acp` (stdio JSON-RPC bridged to WS). Search / get / getMessages / delete are NOT covered by ACP; we run a per-profile `hermes -p <profile> dashboard` sidecar at `acpPort + DASHBOARD_PORT_OFFSET (1000)` that mounts the bundled `sentient-plugin` REST tree. Three architectural lessons: (1) upstream ACP doesn't cover every surface the gateway needs — extending Hermes via plugins (its own concept) fills gaps without forking. (2) The subprocess model (`acp_ws_server` spawns `hermes acp` per connection) beats the in-process `acp.run_agent(HermesACPAgent())` path because it inherits Hermes' CLI-level profile bootstrap (model resolution, .env loading, credentials) for free. (3) The profile-renderer must regenerate per-user `config.yaml` on every gateway boot; otherwise stale models/MCP catalogs land at the worker. See `gateway/src/admin/boot-migration.ts#renderConfigsForExistingUsers`. Apply / restart / dispatch-reset paths are stubbed under ACP — see `docs/research/2026-05-08-apply-restart-acp-rewire-todo.md`.
- [2026-06-11] One-bubble identity: the duplicate "full reply + typewriter" bubble (and its webui twin) came from BOTH clients **inventing** a `cycleId` for committed assistant entries instead of reading the gateway's. The gateway already tags every `conversation.entry` FRAME with `cycleId` (`hermes-event-translator.ts` emit), but `conversationEntrySchema` dropped it, so the clients reverse-engineered it: webui by ts-proximity (`cycle-helpers.ts` `CYCLE_ID_WINDOW_MS` stamp), mobile by exact text-match (`StateDeriver.stampCycleIds`). Both held in the happy path but broke on reconnect / REST-refetch / interrupt → committed twin not suppressed → two bubbles. Fix = make the gateway the source of truth: add `cycleId` (optional) to the `conversation.entry` frame schema (gateway already emits it), read it through on every client (web-sdk `CommittedFeedItem`, mobile `ConversationFeedItem.Assistant.cycleId` re-attached by `ConversationHistoryConnector`), and **delete** both derivation hacks. Suppression by exact `cycleId` then holds everywhere. Also keyed UI rows by the stable gateway id (`cycleId` assistant / `entryId` user / `pendingId` pending) instead of list index, so the streaming→committed handoff is the same row (no remount). Principle: **clients never invent ids — if you need a correlation id, the gateway already put it on the wire; fix the schema, not the client.** Hermes emits 1 assistant message per turn; future multi-message stays gateway-owned via `cycleId`.
- [2026-06-13] Warm-reconnect lost conversation continuity: a follow-up message forked into a NEW chat. Root cause = `conversationId` (the ACP/Hermes thread id) was keyed to the ephemeral per-WS `sessionId`, so on a warm reconnect the gateway's `recovered:true` early-return in `ws-session-configure.ts` ran BEFORE any re-anchor, leaving the next cycle to lazily `session.new` a fresh thread (`resolveAcpSessionId`). Fix = client asserts its current `conversationId` in `session.configure` (new optional field on `sessionConfigureSchema`, mirrors `resume`); gateway seeds `pendingNewSessionId` from it (or the resume url) BEFORE the `recovered:true` early-return. Same principle as one-bubble: the durable id is the gateway/Hermes thread id, not the connection id — thread it explicitly, never let it ride the ephemeral WS session.
- [2026-07-17] Mobile Maestro settings E2E was slow for four compounding reasons, not one: (1) one cold `maestro test` invocation PER flow, paying the fixed ~42-65s JVM/device-attach cost on every single flow instead of once per batch; (2) login run separately per flow instead of a conditional subflow that no-ops when already authenticated; (3) per-step timeouts stacked past what the actual wait needed (a post-nav visibility check waiting 10-15s when the UI settles in under 1s); (4) animations left on, adding real wall-clock to every transition, plus flows authored blind against full raw hierarchy dumps instead of the MCP's compact `inspect_screen` view. Fix (commit `204f728`): tag every flow with a real surface+behavior taxonomy and drive selection through `qa/mobile/run-e2e.sh --tags` (one warm batched invocation, explicit canonical file-order since `--include-tags` is unordered and incompatible with `flowsOrder`); move login into a conditional `_helpers/` subflow tag `helper`; cap visibility waits at ≤3000ms by default; disable animations for the run; author via MCP `inspect_screen` once per screen then batch-author+batch-run instead of write→run→dump→fix per flow. Measured: a 13-flow batch ran in 515s total vs ~650s of JVM startup ALONE under the old per-flow model. See `agents/docs/testing-knowledge.md` mobile section for the full taxonomy, runner usage, and gotchas.
- [2026-07-28] Parallel plan waves that share ONE working tree break "one logical change per commit / atomic commits" in two specific ways — both hit Plan 3 Wave 2 on `feature/native-orchestrator` (`c7d1647`, `2150e22`, `5c42caa`), and neither is caught by any gate, because the pre-commit hook and the full suite only ever see HEAD. (1) **A resumed implementer commits by step LABEL, not step CONTENT.** The killed/restarted T3 agent ran the plan's `git add <paths>` for "Step 5: commit the config surface", but `session-runtime.test.ts` already held the Step-14 wiring test it had written ahead of order — so the red→green TDD sequence the plan spelled out (write test → confirm it FAILS → wire → commit both) collapsed, and the test shipped two commits before the code that makes it pass. `bun test runtime/session-runtime.test.ts` is red at both intermediate commits; `git bisect`/cherry-pick/partial-revert on that file is broken even though HEAD is green. Guard: before every plan-step commit, `git diff --cached` and confirm the staged hunks are *exactly* the step's content — a path list is not a content check, and a test file named by two different steps will silently carry the later step's work. (2) **A plan can assert "disjoint" file sets that are not disjoint.** T2 (voice) declared itself "the only Wave-2 writer of `session-runtime.ts`"; T3 (compaction)'s Files section authorized the same file; the wave table called them disjoint. Whichever agent commits second finds the other's uncommitted hunks in the shared tree and has to choose between bundling foreign scope (what happened, disclosed in the commit message) and stripping a sibling's in-flight work. Guard: derive wave disjointness by intersecting the tasks' actual Files lists, not by trusting the rationale column; when a shared file is unavoidable, commit the sibling's hunks first under their own `type(scope):` message. Meta-lesson: history defects are invisible to every automated gate — the only detector is a reviewer reading the commit split, so budget for that in multi-agent waves, and prefer squash-merge when a wave's intermediate commits are known non-atomic. Full erratum + binding ownership split: R12 in `docs/superpowers/plans/2026-07-27-sentient-2.0-plan3/README.md`.
- [2026-08-08] Invisible-Unicode lint at skill write-time is fail-closed by design, and it exists for a specific documented attack: a `SKILL.md` body/name/description carrying zero-width characters, Unicode Tags-block characters, or bidi controls is REJECTED at write (`gateway/src/tools/skill-tools.ts`'s `INVISIBLE_CHARS` check, run before the shape/frontmatter validation so the error is legible), not merely flagged. Rationale: self-authored instructions have zero legitimate use for invisible characters, so rejection costs the author nothing (rephrase and retry), while the CSA (Cloud Security Alliance) unicode-in-skill-files research note's attack class — hiding an instruction override inside characters that render as nothing — has no other reliable choke point once the text is on disk and re-entering every future session's context. Contrast with fetched content (below): the same characters in a web page only ever get annotated, never rejected, because the household didn't author the page and can't fix it by retyping.
- [2026-08-08] The inbound-scanning boundary (`gateway/src/security/inbound-gate.ts`) is annotate-don't-block for FETCHED content (tool results, background-completion payloads, the outbound delegation prompt) but reject-at-write for SELF-AUTHORED content (a skill's name/description/body). Same scanner (`scanContent`), two postures, and the axis that decides which applies is authorship, not channel: fetched text is judged against user intent via PDP risk escalation because blocking a legitimate page is worse than a confirm prompt and the user can't rewrite someone else's page; self-authored text can always be cheaply rephrased, and a skill's `description` specifically never transits the inbound gate at all (it renders straight into every future session's system prompt, not as a `tool_result`), so write-time is its only scan point — reject there or never catch it.
- [2026-08-08] Native (in-process, non-MCP) tools that need per-tool permission overrides don't fit the existing `permissions[serverName][toolName]` resolution chain, because `storedPermissionFor` needs a real MCP server key and native tools (`delegateTask`, the five `skill_*` tools) have none. Rather than a new resolution path, the skill system reused the existing one under a reserved synthetic key: `permissions["native"][toolName]`, with `"native"` refused as a real MCP server name at config load so it can never collide with an operator's catalog. The subtlety worth remembering: **the reserved namespace's ABSENCE from the stored table is not "unset" in the failure sense** — the catalog-seeded role template legitimately never carries a `"native"` key (it's built from `mcp_catalog`, which has no native tools), so `stored["native"]` being undefined just means "no override yet," and resolution correctly falls through to `defaultPermissionForTier` the same way it does for `delegateTask`. A resolver that treated a missing `"native"` key as an error rather than as "no override" would have broken every native tool on first boot.
- [2026-06-13] SentientMobileVitals changes the mobile-sdk logging **threat model**: the always-on ring captures every `shared/mobile-sdk` line at DEBUG+ and UPLOADS it to the gateway, so ANY DEBUG log of user/chat content in commonMain is now a privacy leak in the uploaded file — not just an ephemeral logcat line. Two real leaks shipped under the old "DEBUG is ephemeral" assumption and were caught by E2E + holistic review, NOT unit tests: `WsTransport` logged raw inbound WS frames (`recv-text raw=`, chat delta text) and `SessionsConnector`/`SessionsHttpClient` logged the user search query (`q=`). Both fixed to log lengths only. Lesson: `PrivacyGuardTest` must drive EVERY content-bearing sink (it now drives `WsTransport.routeText` + `SessionsConnector.search`, not just `InFlightMessageConnector`); when auditing mobile logging, grep for any log value that is content not a length/id/type. Also: at crash time the platform `deviceSnapshot()` runs in the DYING process — keep those reads best-effort/non-throwing (and prefer cheap ones; Android `ConnectivityManager`/`ActivityManager` are Binder IPC that could block).
