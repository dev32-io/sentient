# Sentient 2.0 — Native LLM Orchestrator (Walking Skeleton) — Design

- **Date:** 2026-07-23
- **Branch:** `feature/native-orchestrator`
- **Status:** Design approved; pending spec review → implementation plan
- **Scope of THIS spec:** the walking skeleton (Slice 1). Downstream capabilities (memory, skills, sub-agents, advanced compaction) are named but specified in their own later specs.

---

## 1. Thesis

Sentient 2.0 makes the gateway a **native LLM orchestrator**. The gateway owns the entire agent harness — system prompt, ReAct loop, tool-call format, permission mediation, prompt caching, and compaction — running the LLM call itself over an OpenAI-compatible provider. Hermes is demoted from the agent runtime to **one tool** in a general delegation category.

The Mac mini is the containment boundary. Over-sandboxing (per-user containers, layered proxies as the *primary* isolation line) is relaxed in favor of **capability-based security enforced in code**: careful tool limits, fail-closed permission mediation, and dynamic classification of delegated work.

The architecture is a thin cerebrum core plus capabilities that attach as clean, independently shippable additions. This spec delivers the **walking skeleton**: the smallest thing that talks end-to-end through the native brain against the real web + mobile clients.

### 1.1 Why rewrite, not migrate

The current gateway is a thin ACP client over per-user Hermes workers. 2.0 inverts that ownership. The existing cerebrum (`AttentionGate`, salience, `ShortTermContext` ambient, `ConversationMirror`, the ACP wire pool / surface-lease machinery) is built around the invariant "every cycle = one Hermes round-trip," which 2.0 discards. **Legacy constructs are deleted wholesale, not adapted.** Reusing them would drag a Hermes-shaped model into a native-brain design and corrupt the new boundaries. New code starts fresh; the only things retained are genuinely orthogonal primitives (auth gate, `UserPrincipal` identity anchor from PR #26, security primitives, STT/TTS pipeline, provider catalog fetchers).

### 1.2 Explicitly out of scope for the skeleton (later specs / deferred)

- **Ambient / proactive dispatch** (AttentionGate + salience + sensor sources) — **removed** now, re-architected later against the new principal + role model. Requires a system/home/operator role model that is its own effort.
- **Gateway-owned long-term memory**, **skills**, **recursive sub-agents** — named here, each its own spec.
- **Dreaming** (nightly summarization session), **rolling daily session**, **shared family memory space** — future; the session and memory models must stay flexible enough to admit them.
- **Advanced compaction strategy** — v1 uses provider server-side compaction; custom strategies later.
- **Follow-up task (not in this spec):** rewrite `deploy/mac-prod/setup-prod.py` + install wizard for native-Hermes (drop the dockerized/supervised Hermes lifecycle). Dev assumption: Hermes is already installed natively on the dev Mac and dialed as a local process.

## 2. Tenancy & isolation model

**Single multi-tenant orchestrator process** serving all family members. OS-process-per-user isolation is dropped; the Mac mini is the containment box. Privacy is preserved by a **capability-based security model** that removes ambient authority — the documented root cause of both cross-user leaks and confused-deputy failures in agent systems.

This builds directly on the invariants shipped in **PR #26** (`231f81a`, 2026-07-18):

- **Immutable identity post-auth.** `UserPrincipal` is minted once at the auth gate from the validated token and is `readonly`. Account switch = re-auth = fresh principal. (In current code: `ws-auth-gate.ts` sets `userId` once; `rebind` was deleted. 2.0 keeps this and formalizes `userId: string` into a `UserPrincipal { userId, role, householdId }` value object.)
- **No client-supplied key in a process-global namespace.** All per-user state is owned by the user's scope, never a global map keyed on a client-supplied id.

### 2.1 The four security layers

Ambient authority (a floating "current user" any component can read) is the failure mode single-tenant invites. We eliminate it by minting capabilities from the principal and **passing them down** — object-capability style. No component looks up "the current user."

```
L0  IDENTITY ANCHOR      UserPrincipal — immutable, minted once at auth from the
                         validated token. readonly { userId, role, householdId }.
                         Never passed to tools directly.
        │ principal
        ▼
L1  AccessManager        Capability MINTING. grant(principal, resourceClass) →
                         Capability token, attenuated (least authority). The ONLY
                         place a principal becomes authority. Owns the map:
                         principal → { data dirs, memory scope, tool set, budgets }.
        │ capability (by value)
        ▼
L2  Resource handles     Hold capabilities, NOT the principal. SessionStore,
                         FileScope, ToolBroker, ProviderClient each accept a
                         Capability and physically cannot address outside its grant.
                         No ambient "currentUser" anywhere.
        │ every side-effecting call
        ▼
L3  PDP / PEP mediation  Complete mediation at the tool-call boundary. For EACH
                         proposed call + ARGUMENT VALUES: fail-closed, tiered by
                         side-effect. Exposing a tool is NOT authorization.
```

**Load-bearing principle (from the 2026 confused-deputy research):** a model-emitted tool call is *not* an authorization decision. Once the LLM has read untrusted content (a web page, an MCP result, a delegation output), its tool calls cannot be trusted as authorization. L1 says "you *may hold* the email tool"; L3 says "you may *not send this* email to *this* address *now*." Both are required, and they are distinct layers — merging them into one "manager everyone queries with the current user" re-introduces ambient authority.

### 2.2 L3 trust posture — tiered by side-effect

The default is a function of the tool's **risk class**, not one global switch. This is the only posture that honors both "relax sandboxing" and "careful tool limits":

| Risk class | Default | Notes |
|---|---|---|
| Read / low-risk (queries, home-assistant reads, search) | **allow** | low friction, capable |
| Write / side-effecting / spend / external comms | **deny → confirm** (real permission prompt) | not auto-approved |
| Argument-value violations (e.g. filesystem write outside the principal's scope) | **hard deny** | value-aware, overrides upward |

"More security layers later" = tightening tiers + wiring the currently-dormant primitives into the path — not re-architecting.

### 2.3 Delegation tools — a distinct security category

`delegateTask(agent, taskPrompt)` (see §5.4) is not a structured-arg tool. Its input is a **free-form prompt written by the orchestrator LLM**, and the delegated worker is **broadly capable by design** — clipping its authority defeats the purpose. Fixed value-rules cannot mediate a free-form prompt, so the guard is split:

1. **Static frontmatter envelope** (per `agent` enum value) — a claude-code-skill-style header: `allowed_tools`, `denied`, `network`, `confirm_class`. Coarse capability envelope. **This is deliberately the reference template for the future Skill security layer** — same shape. (No `max_runtime` block-timeout — delegation is a background tool, §5.4.)
2. **Dynamic per-invocation classification** (the load-bearing part) — the LLM-written `taskPrompt` runs through the shared security primitives → **allow / confirm / deny**, classifier-driven ("auto mode"). This is where real safety lives, since #1 cannot constrain free-form intent.

**Accepted risk (flagged, per operator decision):** guarding only the *initial* delegation prompt does not cover a delegated worker being prompt-injected *mid-task* by untrusted content it reads; a natively-run worker's own internal tool calls are outside our PDP. This is accepted to keep the worker capable. **Free mitigation hook:** point the delegated worker's tools at *our* gateway MCP host so its calls re-enter our L3 PDP — a second mediation point at no extra cost.

### 2.4 Shared, reusable security primitives

Encapsulated as a shared module; the DelegationGuard is their first consumer, the future Skill layer their second, the tool PDP a third. One implementation, many callers:

- `InjectionScanner` — prompt-injection pattern scan (exists today, dormant; wired up in 2.0).
- `PromptClassifier` — "auto-mode" risk-tiering of a prompt. New.
- `RiskAccumulator` — exponential-decay risk scoring (exists today, dormant; wired up).
- `ContentScanner` — secret/PII/policy scan of arbitrary text. New (may start minimal).

### 2.5 Physical isolation as cheap defense-in-depth

Code-enforced capabilities are the boundary; OS-level physical separation is a free second layer on top, so a path/config bug can't silently cross users. Both are granted **through the principal** — the capability is what addresses the resource; nothing reads an ambient "current user."

- **Per-user session database.** Each user's history/session store is a separate on-host SQLite file, not a shared multi-tenant table. A query physically cannot reach another user's DB — there is no shared table to mis-scope. (Also the natural WAL concurrency unit — §2.6.)
- **Per-user home/workspace directory.** Each user gets `~/.sentient/gateway/users/<userId>/` (DB, memory, files, scratch). `AccessManager.grant` mints a `FileScope` capability (an L2 handle) bound to exactly that dir. The PDP/classifier **denies any filesystem path outside the granted scope — including reads.** Sensitive per-user data therefore lives in physically distinct directories, and cross-user file access is a hard deny by path, before any content check.
- **Future scopes.** System / operator / HA / anonymous scopes are additional principal *roles* with their own granted scopes (e.g. a shared/system workspace dir). The `UserPrincipal.role` + `AccessManager` grant map is the single extension point; the isolation mechanism is identical, only the grant differs.

### 2.6 Concurrency & isolation model

> **Superseded on the `(userId, surfaceId)` key** by `docs/superpowers/specs/2026-08-02-session-model-and-multi-surface-design.md` §2.5, implemented in that plan's task 5. The isolation model below is unchanged; only the key is.

Sessions are concurrent and mutually isolated. One **`SessionRuntime`** per **`sessionId`** — a server-minted, opaque, CSPRNG id, with **N connections attached to it**, each a window onto the same conversation. It owns its own ReAct loop, its own `ToolBroker` + capability, its own `AbortController`, and its own store handle. No `SessionRuntime` can reach another's state (that reachability *is* the L2 capability boundary).

The retired `(userId, surfaceId)` key made a surface's conversation permanent and single-windowed, and its registry enforced that by EVICTION: a second connection naming the same conversation tore the first one down. Attachment replaces it. The invariant that key was protecting is unchanged and still binding — *two live runtimes on one partition are two ReAct loops appending to one append-only log, each having read prior context without the other's writes, plus two `bun:sqlite` handles contending on one WAL* — so it is now enforced by the subscriber set (`session-handlers/session-registry.ts`), which builds the runtime on the first attachment and releases it only when retention says so.

Execution model:

- **Single-threaded event loop (Bun), async-interleaved.** Concurrency is cooperative I/O interleaving, not OS threads. Every heavy operation is I/O off the loop: the LLM call is network I/O, MCP tool calls are HTTP I/O, `delegateTask → hermes` is a separate OS process. Nothing CPU-blocks the shared loop, so one user's active turn cannot starve another's — provided no handler blocks synchronously.
- **Background delegation removes the one real blocker.** A long delegated task must not hold the loop; §5.4 makes delegation a *background* tool (fire-and-steer), so a multi-minute Hermes run never blocks any turn, that user's or anyone else's.
- **Store thread-safety by construction.** Per-user SQLite (§2.5) in **WAL mode** with a synchronous driver: appends within a user serialize on that user's connection; append-only (Invariant A) means no update/delete race is even expressible; different users hit different DB files, so there is no cross-user write contention at all.
- **Concurrency cap, not a scheduler.** A config `max_concurrent_sessions` bounds live runtimes (family scale — a fair-share scheduler is unnecessary and out of scope). Excess connections queue at accept time, never mid-turn.

Reachability of another user's `SessionRuntime`, store, or dir from a given principal is a **security-boundary invariant**, tested like auth (the principal-isolation contract test, §10).

## 3. Session store — single source of truth

The gateway owns a **durable local database** (embedded, on-host). It replaces both Hermes' durable store *and* the in-memory `ConversationMirror` — those two records can drift today; in 2.0 they collapse into one.

### 3.1 Requirements

- **Survives restart, switch, reconnect.** Persistent "past chats" list, exactly the current UX, but gateway-owned.
- **Full-fidelity mirror of session context.** Every entry that participates in model replay OR client render is stored: `user`, `assistant`, `tool_call`, `tool_result`, `trigger`, `system`, `compaction`. This is the record used to rebuild the model's `messages[]` for continuation AND to rebuild the client feed on reload.
- **Own timestamps.** Every entry carries `created_at`, fixing the Hermes gap (Hermes has no per-message timestamp).

### 3.2 Two invariants (both load-bearing)

**Invariant A — Immutable, additive history.** Committed history is append-only at the interface layer. A new entry (user, assistant, tool_call, tool_result) is *only ever appended* — existing entries are never mutated or reordered. This keeps the model-facing prefix **byte-stable for prompt caching** (the hard-won pre-Hermes lesson: a mutated prior entry busts the cache from that point). The store's write API exposes append + read; it exposes no in-place edit of committed entries.

**Invariant B — Projection convergence.** One canonical entry schema, two *pure* projection functions:

```
                 SESSION STORE (durable, append-only)
                 canonical entries, full fidelity, created_at
                        ┌──────────┴──────────┐
              MODEL projection          CLIENT projection
              entry → OpenAI messages[]  entry → ConversationFeedItem
              (tool_call_id, args,       (rendered tile; may redact
               role:"tool" results)       large/sensitive tool detail)
                    │                          │
              ReAct loop                  wire → web/mobile
                                          SAME path live + replay
```

> **`render(replay(store))` MUST equal `render(live-settled stream)`** — equal in emitted feed items.

Live streaming frames (`message.delta`, running `task.update`) are a smooth-rendering optimization that **must converge** to the committed entry's client projection. Divergence *is* the "weird tile only appears on reload" bug — prevented by construction, not by luck. Every renderable entry kind has its client projection defined **at design time**, before it ships; anything ephemeral is explicitly not stored and must converge to a stored entry's projection when it settles.

This invariant is enforced by a **protocol-contract test** (the kind the testing rules keep): drive a sequence through live-commit, snapshot the feed; replay the store, snapshot again; assert equality.

### 3.3 The in-memory mirror is a view, not a record

Any in-session working view of the conversation is a **read-through / write-through view over the store**, never an independent record. This eliminates the drift class that produced today's `ConversationMirror` vs. Hermes-store divergence.

### 3.4 Compaction is an append; projections diverge (not a mutation)

Compaction never rewrites history. When the provider compacts (§8), the gateway **appends** a `compaction` entry capturing the summary + the boundary it covers. Invariant A holds — nothing prior is mutated or deleted, so all pre-compaction detail survives for client rendering and bookkeeping. The two projections then legitimately diverge, which is exactly what Invariant B allows (one store, two pure functions):

- **Model projection** — reads from the **latest `compaction` entry forward**: the compacted summary followed by every entry after the boundary. This is what feeds the provider `messages[]`; it stays cache-stable (the compaction summary is itself a stable prefix once written).
- **Client projection** — reads the **full** entry stream, ignoring `compaction` boundaries for the feed (a `compaction` entry may render as a subtle "earlier conversation summarized" marker, or nothing). The user still sees complete history; nothing disappears from the feed because the model's context was compacted.

So compaction shrinks what the *model* replays without shrinking what the *store holds* or what the *client shows*. Immutable store, divergent projections — the invariant is the mechanism.

**Boundary safety — never split a tool-call pair.** A compaction boundary landing between a `tool_call` and its matching `tool_result` would make the forward slice start with a dangling `role:"tool"` message that has no preceding `tool_calls` — malformed `messages[]` that the provider rejects. Two defenses:

1. **Snap to a safe point.** The recorded boundary is always snapped to a turn/iteration boundary — a point where no tool call is outstanding. Never mid-pair.
2. **Defensive projection repair.** The model projection additionally drops any leading `tool_result` that has no matching `tool_call` in the slice. Belt and suspenders: if a provider-side boundary ever lands mid-pair, the projection still emits a valid message array.

## 4. Orchestration core — the native ReAct loop

The gateway runs a **full ReAct loop** natively. No shortcut path. This is our own harness — comparable in ownership to codex / claude-code / an agent SDK — and we own every part that matters: system prompt, the loop, when to stop, caching, compaction, and the L3 PDP gate between "model asks" and "tool runs."

### 4.1 Provider — OpenAI-compatible only

All current and future target models are OpenAI-compatible. The provider client speaks the OpenAI Chat Completions shape (`messages`, `tools`, `tool_calls`) over HTTP — reusing the proven pre-Hermes streaming + tool-call-concat pattern (`import OpenAI`, `chat.completions.create({stream:true, tools})`, accumulate `tool_calls` deltas by index, flush on `finish_reason: "tool_calls"`). OpenRouter + local Ollama (uncensored / `unlimited_mode`) are both reachable. The client sits behind a `ProviderClient` interface so alternates are a clean later add; the Anthropic wire shape is explicitly **not** needed.

### 4.2 Native function-calling, not prose parsing

Tools live in the dedicated `tools` request field (JSON Schema); tool calls come back in the dedicated `tool_calls` response field. We do **not** scrape tool calls out of prose. The only parsing is `JSON.parse(arguments)` on a well-formed string, plus streaming delta accumulation by index. A `ToolCallCodec` interface abstracts this: the `native` impl (read `tool_calls`) ships now; a `parsed` impl (scrape an own text format, for completion-only local models) is a clean later add.

### 4.3 The loop

```
1. Build request: system + immutable tools[] + messages[] (from store, model projection)
2. POST (stream) to ProviderClient        [respects the turn's AbortSignal]
3. Response has tool_calls?
   ├─ no  → finish_reason "stop" → append assistant entry → cycle done
   └─ yes → for each call:
              JSON.parse(args)
              ── L3 PDP CHECK (allow / confirm / deny) ──
              dispatch by tool category (§5.2):
                foreground → await result       → append tool_call + tool_result
                background → get {taskId} now    → append tool_call + task-started
                                                   (task runs off-loop; result
                                                    arrives LATER as a stimulus, §4.4)
            → goto 1   (this back-edge is the ReAct loop)
```

Bounded by a config `max_iterations`. The L3 check sits exactly between the model *asking* and the tool *running* — the complete-mediation point. Text deltas are forked to TTS as they stream (§6). The whole loop respects the turn's `AbortController` (§4.7): on abort it stops consuming the provider stream, stops issuing tool calls, and yields without throwing.

### 4.4 Stimulus-source seam (ambient-ready, ambient-absent)

The loop's entrypoint is an abstract, **source-agnostic stimulus seam**. A stimulus is simply "something was appended to the store that the model should see." The skeleton wires **two** sources:

1. **Conversational** — a user text/voice message.
2. **Background-task completion** — a background tool's result arriving off-loop (§5.2).

Later sources (ambient sensors, the re-architected attention model, explicit user mid-turn steer — §4.5) attach to this same seam without touching the core. The skeleton has *no* salience, *no* gate, *no* debounce — a stimulus lands, §4.5 decides whether it steers the running turn or starts the next one.

### 4.5 Turn serialization and steer

**At most one turn (ReAct loop) runs per `SessionRuntime` at a time.** A stimulus never spawns a second concurrent loop — concurrent loops in one session are what produce torn feeds and overlapping speech.

**The store is the queue.** Every stimulus appends to the append-only store; `SessionRuntime` tracks a `lastProcessedSeq` high-water mark. There is no separate queue structure — the append-only log plus a sequence marker *is* the queue. This is the deleted `AttentionGate`'s turn-backpressure (*fire at turn end with everything since the last turn ended*) **minus salience, debounce, and thresholds**.

**Steer — the general mechanism.** The loop rebuilds `messages[]` from the store's model projection at the top of **every iteration** (§4.3 step 1). So a stimulus appended while the loop is mid-flight is picked up on the next iteration automatically: the model sees the new information and course-corrects **within the same turn, same bubble**. No interrupt, no discarded work. This is **fire-and-steer**, and it is a property of the *seam*, not of any one tool — it works identically for background-task completions today and for ambient events or explicit user mid-turn steer later. Any source that can append can steer.

**Steer vs. next turn — the boundary.** The test is whether the loop can still absorb it:

| Loop state when the stimulus lands | Outcome |
|---|---|
| Mid-iteration (more tool calls coming; final answer not yet committed) | **Steer** — absorbed by the next iteration's store re-read; same turn, same bubble |
| Already streaming its final answer (`finish_reason: stop`; no further iteration) | **Next turn** — a fresh back-to-back turn fires at turn end with everything since `lastProcessedSeq`; new turn id, new bubble |

The boundary needs no extra signalling: it is simply "did another iteration occur after the append." Once the loop has committed to a final answer, no store re-read can retroactively help, so it must be a new turn.

**Self-interruption is forbidden.** A gateway-initiated follow-up turn NEVER stops or flushes in-flight TTS (§4.7, §6). Only the user interrupts audio.

### 4.6 Immutable tool set

`tools[]` is **immutable per session** — never mutated per turn. This is both a caching property (tools render first in the cached prefix; any change busts it) and a security property (hiding a tool is not a boundary; the boundary is L3 at the call). The model always sees the full permitted-at-mint tool set; per-call permission is enforced at execution. The tool set is a small fixed vocabulary: MCP-catalog tools (reads) + `delegateTask` + a few motor/system tools.

### 4.7 Cancellation — barge-in vs. interrupt

Each `SessionRuntime` owns the current turn's `AbortController`. Two cancellation paths, both **outside** the loop (they hit the abort directly; the loop observes the outcome):

| Path | Trigger | Aborts | Keeps |
|---|---|---|---|
| **Barge-in** | mic onset (user starts speaking over TTS) | current turn + TTS playback | background tasks (§5.4) — user is talking, not cancelling the work |
| **Interrupt** | UI Stop / Esc | current turn + TTS playback | background tasks (§5.4) — see below |

On abort the loop stops consuming the provider stream and stops issuing tool calls without throwing (per the AbortSignal decorator rule). The partial assistant output is committed as an entry with a **cutoff kind** (`interrupt | barge-in`) — an append, so history stays immutable (Invariant A) and the client can render "interrupted here."

**A background task outlives the turn that spawned it in every case, and nothing cancels it.** This supersedes the earlier draft, in which interrupt fanned out into a blanket `BackgroundRegistry.cancelAll()` — an all-or-nothing sweep of every delegation in the session, triggered by a gesture the user makes about the *reply*. The two gestures now differ only in the cutoff kind they stamp. Consequences, accepted deliberately:

- a runaway delegation runs to its own completion; the **lost-task watchdog is the only backstop**;
- `cancelledTaskIds` on the `interrupt` cutoff frame is always empty, and accurately so;
- session **retention** (§5) is therefore the whole mechanism keeping a delegated task's result reachable — the store handle must stay open until the completion lands.

The per-task `cancel` handles stay registered. They are the mechanism for a later **model-facing task-management tool**, which cancels by *named* taskId — the granularity a blanket sweep could never offer, and the reason this is a deferral rather than a removal.

**TTS interruption is user-only.** Barge-in and interrupt are the *only* events that stop or flush TTS. The gateway never stops its own audio: a self-initiated follow-up turn (§4.7) emits a new turn's audio that the client **queues behind** whatever is still playing (§7.2). There is no gateway-emitted "stop audio" for self-initiated work.

This is the skeleton's cancellation surface. Ambient-salience clearing on interrupt (today's `AttentionGate` behavior) is **not** in the skeleton — there is no ambient accumulator yet; it returns with the re-architected ambient model.

## 5. Tools

### 5.1 MCP client (new)

The skeleton's tool surface is the **existing MCP servers** reused as tools. Today the gateway *hosts* an MCP server for Hermes to call (`mcp-host/`); 2.0 adds the inverse — an **MCP client** that dials the same `http://<service>:<port>/mcp` endpoints (home_assistant, search, fetch, gateway-hosted tools) and exposes their tools to the native loop. MCP *is* the tool-call substrate; no bespoke tool registry for v1. The MCP deployment rule (one container per MCP, HTTP transport, no host ports) is unchanged — tool egress containment stays at the container boundary, independent of where the brain runs.

### 5.2 Tool categories — foreground vs. background

Every tool declares one of two execution categories. This is a first-class distinction in the loop (§4.3), not a per-tool detail:

- **Foreground (fire-and-wait).** The loop `await`s the result before continuing. The model blocks on it. Quick, bounded operations: MCP reads, home-assistant queries, motor/system tools. Result is appended as `tool_result`; the loop iterates with it in context.
- **Background (fire-and-steer).** The tool returns a `{taskId}` handle *immediately*; the work runs off the loop and does **not** block the turn. The loop continues — the model can respond to the user, launch parallel background tasks, or cancel. This is **fire-and-steer, not fire-and-forget** (the established async-subagent pattern): the supervisor stays in control.
  - **Completion is interrupt-driven, not polled.** When a background task finishes, its result is appended to the store as a **stimulus on the §4.4 seam**, which either steers the running turn or fires the next one (§4.7). No status-polling loop (polling wastes tokens on every check).
  - Progress surfaces to the client as `delegation-progress` frames (§7); the running task is **not** cancellable by any gesture — it outlives the turn (§4.7).
  - **Bounded:** a config `max_concurrent_background_tasks` per session (default **50** — generous for family scale; a real resource monitor is later work). Exceeding it fails the tool call with a "too many running tasks" result the model can act on.

The general rule: promote a tool to *background* when it is long-running enough that blocking the turn would freeze the conversation. Delegation is the archetypal background tool.

### 5.3 Tool execution + PDP

`ToolBroker` (an L2 resource handle holding a capability) executes tool calls via the MCP client, dispatching by category (§5.2). Every call passes L3 mediation first (§2.2). The reusable `PolicyEngine` (exists today, `allow`/`deny`/`confirm`) is hardened: **fail-closed default for side-effecting tools** (today it fails open — no rule → allow) and **`confirm` becomes a real permission prompt** (today auto-approved), delivered as a new wire frame (§7) with real client UI (§7.1).

### 5.4 `delegateTask` — the generalized delegation tool (background)

A single immutable tool slot collapses N present and future agentic workers, and it is a **background** tool (§5.2) by design — delegation is long-running and must not block the loop:

```
delegateTask(agent: "hermes" | "opencode" | "codex" | ..., taskPrompt: string) → { taskId }   // returns immediately
```

The model dispatches a task and keeps talking; the worker runs off-loop; its result returns later as a stimulus (§4.4). Adding a future agent = one enum value + one DelegationGuard frontmatter entry; **zero new tool slots, zero prompt-size growth, zero cache impact**. The static frontmatter (§2.3) carries the coarse envelope (`allowed_tools`, `network`, `confirm_class`) — **not** a `max_runtime` block-timeout (the discarded design; background tasks aren't timed-blocks). For the skeleton, only `agent: "hermes"` is implemented, dialing the natively-installed local Hermes process (multiple concurrent CLI invocations are fine — Hermes is a separate process per call). Guarded by the DelegationGuard (§2.3); once dispatched it runs to completion — nothing cancels it (§4.7).

## 6. Voice — STT / TTS on the native stream

STT and TTS already bypass Hermes today (the gateway owns the full audio pipeline; Hermes never sees audio). The **only** change in 2.0: the text-delta source feeding TTS moves from the Hermes stream to the **native loop's** streamed assistant deltas. STT output becomes a user entry in the store → triggers a cycle (§4.4) → the native loop's text deltas fork into the TTS pipeline. Both services stay on-host, dialed over WS, unchanged internally.

## 7. Client wire contract

The web + mobile (KMP SDK) clients are live and consume a defined SDK protocol. 2.0 keeps the contract as a **stable seam** — the native loop emits client frames directly (no Hermes-stream translation in the middle) — with **latitude to evolve names and add/remove frames** where 2.0 semantics differ. Both client SDKs update in lockstep; this is a coordinated change, not free.

- **Rename where semantics shifted** — e.g. `cycle.*` (named for "one Hermes round-trip") may become `turn.*` for a native turn. Not preserved out of timidity.
- **New frames 2.0 requires:**
  - **Permission-prompt request/response** — for L3 `confirm` decisions (§5.3); rendered as a real dialog (§7.1).
  - **Delegation progress** — for background `delegateTask` work (§5.4).
  - **Cancellation** — barge-in / interrupt signals + the cutoff-kind marker on the committed partial (§4.7).
- The internal event type feeding the wire is fresh/clean (we own it now); the bytes on the client socket remain a defined, versioned contract.

The client render path is the **same for live and replay** (§3.2), so no reload-only frames exist.

### 7.1 Permission-prompt UI (required for the skeleton to walk)

An L3 `confirm` decision (§5.3) is not walkable without a user-facing prompt — a headless confirm blocks the turn with nothing to approve. The skeleton therefore ships the permission dialog on **all live surfaces**, using each platform's existing design language (no new design system):

- **Web (Preact / webui):** a modal dialog in the existing component style — tool name, human-readable action + argument summary, Allow / Deny. Bound to the permission-prompt wire frame; blocks the turn until answered.
- **Android (Compose):** an equivalent dialog via the existing Material/M3 patterns and the KMP SDK's state surface.
- **iOS (SwiftUI):** an equivalent dialog via the existing SwiftUI patterns and the same KMP SDK state.

The prompt is driven entirely by SDK-emitted state (per the state-bound-UX rule): request frame in → dialog renders; user decision → response frame out → PDP resolves. On deny, the tool is blocked and the model receives a "user declined" tool result so it can adapt. **Timeout: 2 minutes** (config-tunable) → **auto-deny**, dialog dismisses, and the model receives a "permission request timed out" tool result. Fail-closed: a timeout is never an implicit approval.

### 7.2 Client audio queueing (self-initiated follow-up turns)

Because the gateway never interrupts its own TTS (§4.7), a follow-up turn (§4.5) produces a **second** assistant turn whose audio arrives while the previous turn's audio may still be playing. Clients must handle this:

- **Queue, don't replace.** TTS audio is played as a sequential queue keyed by turn id. A new turn id does NOT cancel or replace the in-flight stream — it plays after it.
- **Two bubbles.** Each turn renders its own feed entry. Two consecutive assistant bubbles with two turn ids is a valid, expected state.
- **Flush only on user action.** The audio queue is flushed *only* on barge-in (mic onset) or interrupt (Stop) — never on a new turn id.

This is a real change on both client SDKs (web + KMP): current clients assume a single active TTS stream per session and may cancel on a new turn. It is an explicit implementation task, not a free consequence of the server change.

## 8. Compaction

> **Amended 2026-07-27.** This section originally specified *provider server-side* compaction via the OpenAI-compatible `context_management` / `compact_threshold` field. That is not implementable on the endpoint this design commits to: in `openai@6.49.0`, `context_management` exists **only** on the Responses API (`client.responses.create`) and is absent from `ChatCompletionCreateParamsBase` — while §4.1 explicitly pins the gateway to the Chat Completions shape, and neither configured provider (OpenRouter, Ollama Cloud) is verified to implement Responses at all. v1 is therefore **gateway-side compaction**, decided by the operator on 2026-07-27. Everything below about the store, the entry, and the projections is unchanged and remains correct.

v1 uses **gateway-side compaction**: the orchestrator counts context against a config threshold (`orchestrator.compaction.compact_threshold_tokens`), and on crossing it issues its own summarization call through the existing `ProviderClient`. On a compaction event the gateway **appends a `compaction` entry** (summary + covered boundary, snapped to a safe non-mid-tool-pair point per §3.4) to the store; the store keeps the **full** pre-compaction history (with our timestamps). Projection then diverges by design (§3.4): the **model** projection replays from the latest `compaction` entry forward (compacted, cache-stable, with dangling-`tool_result` repair); the **client** projection still renders full history. The persisted compaction state makes continuation work across restarts. Threshold is config-tunable. Custom strategies (percentage tuning, the nightly "dreaming" summarizer) are later work built on this seam.

> **Implementation note (Plan 3 Task 3, 2026-07-27).** The producer ships as
> `gateway/src/runtime/compaction.ts`, called from `SessionRuntime`'s settle
> path — after the turn's terminal frame, before the one-turn lock clears —
> because the model projection slices **positionally** from the latest marker:
> a marker covers every entry appended before it regardless of
> `compactedThroughSeq`. Two consequences follow. The boundary is always the
> store's tail, so an unsafe tail (a trailing `tool_call`) is *refused* and
> retried at the next turn end rather than snapped backwards; and
> `orchestrator.compaction.keep_recent_turns` means "rendered verbatim inside
> the marker's own text", not "left after the marker" — nothing can survive
> after an append-only marker. Switching to the provider-native Responses path
> later stays a drop-in provider-layer swap: the entry model, both
> projections, and these config keys are identical either way.

## 10. Walking-skeleton acceptance (Slice 1)

The skeleton "walks" when, against the real local stack and real web + mobile clients:

1. A user authenticates → immutable `UserPrincipal` minted; a capability + per-user DB + per-user home dir are granted via `AccessManager`.
2. A text or voice message is stored (append-only, timestamped) → triggers one native ReAct cycle in that user's isolated `SessionRuntime`.
3. The native loop calls the provider (OpenAI-compatible, streaming), issues at least one **foreground** MCP tool call, which passes L3 mediation, executes, and its `tool_call` + `tool_result` are appended to the store.
4. `delegateTask("hermes", …)` dispatches as a **background** task (returns `{taskId}` immediately, does not block the loop), passes the DelegationGuard; its result later arrives as a stimulus and is appended to the store.
5. **Steer:** a background result landing mid-loop is absorbed by the running turn (same bubble); one landing after the final answer fires a back-to-back follow-up turn (new bubble) whose audio **queues behind** the still-playing TTS — the gateway never stops its own audio.
6. Assistant text streams to the client AND forks to TTS; STT feeds the input path.
7. **Barge-in** (mic onset) and **interrupt** (UI Stop) both abort the turn + TTS and both keep background tasks running (§4.7 — nothing cancels a background task); the partial is committed with a cutoff kind.
8. A side-effecting tool triggers a **real permission dialog** on web and mobile (L3 `confirm`), not auto-approval; approve executes, deny blocks + informs the model; a 2-minute timeout auto-denies.
9. On reload / session-switch / restart, the past-chat list and full feed rebuild from the store, and **`render(replay) == render(live)`** — no reload-only tiles.
10. Two family members in one process never see each other's data, DB, or files — cross-user file access is denied by path (principal-isolation contract test green).
11. A compacted session continues correctly: model replays from the compaction marker, client still shows full history.
12. **One turn at a time per session** — no concurrent loops, no overlapping generation, regardless of how many stimuli land.
