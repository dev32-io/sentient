# Phase 3.5: Voice WebSocket Wiring — Tracking Doc

> **This is NOT a full implementation plan.** It is a tracking doc for deferred scope.
> Before executing, run `/superpowers:writing-plans` to produce a detailed task breakdown.

## Why this exists

Phase 3's stated goal was "toggle-to-talk voice works in Chrome + Safari." Its 17 tasks delivered all **client-side** audio infrastructure (capture hook, worklet, ring buffer, playback hook, UI) but did **not** wire STT → LLM → TTS into the gateway's WebSocket message handler. Phase 4's preamble assumes the voice loop is working end-to-end, confirming this was a planning omission rather than a deliberate deferral.

Phase 2 built the voice providers as pure library code. `gateway/scripts/try-voice.ts` demonstrates an MP3 → WAV pipeline using those providers. None of it is plumbed into `ws-server.ts`.

## Scope

Wire the end-to-end voice loop over the existing WebSocket protocol:

```
Client                        Gateway
─────────────────────────────────────
audio.start  ──────────────►  start STT session (Deepgram)
binary audio ──────────────►  forward to STT
binary audio ──────────────►  forward to STT
audio.end    ──────────────►  finalize STT
                              ◄── transcript.final (optional, for UI echo)
                              LLM stream (OpenRouter)
                              ◄── response.text.delta (stream)
                              sentence aggregator → TTS (Fish Audio)
                              ◄── binary audio frames (Float32)
                              ◄── response.audio.done
barge_in     ──────────────►  cancel in-flight LLM + TTS
                              ◄── barge_in.ack
```

## Hard decisions before writing the plan

### 1. Client capture format: WebM/Opus vs raw PCM16

**Current state:** Client uses `MediaRecorder` with `audio/webm;codecs=opus`, produces WebM-containerized Opus chunks every 100ms.

**Problem:** Deepgram's `encoding: "opus"` wants raw Opus packets, not WebM-container. Two paths:

- **(a) Demux WebM on gateway** — add a WebM parser/demuxer, strip the container, forward raw Opus frames. Complicates the server. Matches existing client code.
- **(b) Switch client to AudioWorklet-based PCM16 capture** — bypass `MediaRecorder`, pipe mic stream through an `AudioWorklet` that outputs raw Int16 frames. Simpler server (Deepgram takes PCM16 directly, already the default). Bigger client refactor; loses Safari Opus polyfill relevance.

**Recommendation:** (b). Cleaner end-to-end. Kills the Safari polyfill complexity. Matches what `deepgram-provider.ts` already defaults to (`linear16` at `STT_DEFAULTS`).

**Implication:** The `use-audio-capture.ts` hook and `playback-worklet.ts` twin (a new `capture-worklet.ts`) need rework. The `useSafariPolyfill` hook can be deleted (the `opus-media-recorder` dependency removed).

### 2. TTS output format: PCM vs Opus vs MP3

**Current state:** `TTS_DEFAULTS.format = "opus"`. Fish Audio emits Opus-encoded bytes.

**Problem:** The client's `handleBinaryMessage` in `app.tsx` assumes raw `Float32Array` samples (`new Float32Array(data)`). Opus requires decoding via `AudioContext.decodeAudioData` (async, chunk-at-a-time is awkward) or a JS Opus decoder.

**Options:**
- **(a) Switch TTS to PCM16** — add an Int16 → Float32 conversion in `handleBinaryMessage` (6 lines). Larger bytes on the wire (~10× Opus) but localhost has no bandwidth concern, and we're already using an `AudioWorklet` that expects Float32.
- **(b) Keep Opus, add decoder** — use `@ffmpeg/ffmpeg` or `libopus-wasm` on the client. Heavy dependency. Adds ~200KB to the bundle.
- **(c) Use MP3 + `decodeAudioData`** — each MP3 frame decodes to AudioBuffer; chunked streaming through `decodeAudioData` has known quirks (boundary artifacts).

**Recommendation:** (a). Simplest diff, no new dependencies, localhost bandwidth is free. If production bandwidth ever matters, revisit with Opus decoder.

### 3. Barge-in cancellation semantics

When the client sends `barge_in`, the gateway should:
1. Abort the in-flight Deepgram STT stream (if active).
2. Abort the in-flight LLM stream (`AbortController` on `llmProvider.stream`).
3. Abort the in-flight Fish Audio TTS stream.
4. Clear any buffered TTS bytes still queued for the client.
5. Reply with `barge_in.ack` so the client can clear its playback ring buffer.

All four abort points already exist as `AbortSignal` parameters on the providers. Need a per-session `AbortController` that `barge_in` can call `.abort()` on, and per-turn sub-controllers for finer cleanup.

### 4. Session vs turn lifecycle

A "voice turn" is `audio.start` → (audio) → `audio.end` → (transcript, LLM, TTS) → `response.audio.done`. A "session" spans the WebSocket lifetime. Must decide:
- STT provider connection: per-session (persistent) or per-turn (connect/disconnect each time)?
- Per-session gives lower turn latency; Deepgram's keep-alive semantics need checking.
- Per-turn is simpler; ~200ms connect overhead per turn.

**Recommendation:** Per-session for STT. Connect on first `audio.start`, reuse until socket closes. Matches how text chat keeps the OpenRouter client warm.

### 5. Error paths

- STT connection fails → send `error`, don't attempt to proceed to LLM.
- LLM stream fails mid-response → send partial `response.text.done`, skip TTS.
- TTS stream fails → send `error`, LLM text already delivered via delta stream.
- Network drop during voice turn → session cleanup in ws `close` handler must abort all three providers.

Need a consistent error code taxonomy: `stt_error`, `llm_error`, `tts_error` (or reuse `provider_error` generically).

## Testing strategy

- **Unit:** voice-turn state machine transitions, error paths, abort propagation.
- **Integration:** mock STT/LLM/TTS providers, drive a full turn through the ws handler, assert message sequence and binary frame emission.
- **Manual:** Playwright + real providers for one "hello voice" smoke test. Costs real API credits — gate behind an env var so CI doesn't burn money.

## Acceptance

1. Open the web client in Chrome, grant mic, click mic button, speak a short sentence, click stop.
2. See transcript appear in chat.
3. See assistant response stream in as text.
4. **Hear** the response via TTS through the AudioWorklet.
5. Click the mic again mid-TTS → barge-in cancels playback within 200ms, STT starts for the new turn.
6. Close the browser tab → gateway cleans up all three provider connections without errors.

## Not in scope

- Safari support for PCM16 capture (AudioWorklet is well-supported but edge cases exist).
- Multi-turn context retention beyond what Phase 1 already does for text.
- Voice activity detection (VAD) on the client.
- Noise suppression tuning.
- Any of Phase 4's classifier/security work.
