## M-3: SSE function_call arguments streaming

- Test tool: `terminal` (built-in) — invoked via `model: "hermes-agent"` (full agent loop)
- Events observed (enumerated from SSE trace):

| Event | Count (terminal tool) |
|---|---|
| `response.created` | 1 |
| `response.output_item.added` | 1 (function_call) |
| `response.output_item.done` | 1 (function_call) |
| `response.output_item.added` | 1 (function_call_output) |
| `response.output_item.done` | 1 (function_call_output) |
| `response.output_item.added` | 1 (message) |
| `response.output_text.delta` | 2 |
| `response.output_text.done` | 1 |
| `response.output_item.done` | 1 (message) |
| `response.completed` | 1 |

- `function_call_arguments.delta` JSON schema: **N/A — event not emitted**
- Function call arguments arrive as a complete JSON string in the `function_call` output item's `arguments` field, not streamed token-by-token.
- Verdict: **ABSENT**

### Implication
- `speak-as-streaming-tool` NOT unlockable via Responses API SSE stream. The tool call arguments are emitted atomically, not as deltas.
- Phase 1.3 TTS decorator chain operates on `response.output_text.delta` only — the v4 default design.
- The `function_call` and `function_call_output` items ARE present in the stream, which means the gateway can observe tool call lifecycle (what tool was called, what it returned) but cannot stream tool call arguments token-by-token.
- The text deltas (`response.output_text.delta`) DO stream token-by-token with reasonable chunk sizes (~10–30 chars per delta), which is suitable for TTS.

## M-4: SSE disconnect → server-side halt

- Disconnect at: T+2s (timeout killed curl mid-stream)
- Tokens delivered to client: only `response.created` event (agent was still thinking / in tool call when disconnected)
- Hermes container logs after disconnect: `⚡ Interrupted during API call`
- Server-side halt time estimate: <1 s after client disconnect (log appears immediately)
- Verdict: **HALTS**

### Implication
- SSE disconnect is our reliable interrupt primitive. Proceed with D-8 as-is.
- Hermes detects the client disconnect and interrupts the LLM API call server-side, stopping token generation.
- No need for a follow-up `DELETE /v1/responses/{id}` call (though Hermes may support it — not tested).
- This means our `HermesClient` can simply close the SSE connection to abort an in-flight response, and the server will stop generating tokens within ~1 s.

## M-5: Concurrent request isolation

- 3 concurrent requests fired to same profile (same auth key, same endpoint)
- Request 1 output: "request 1"
- Request 2 output: "request 2"
- Request 3 output: "request 3"
- Verdict: **ISOLATED**

### Implication
- No per-profile mutex needed in `HermesClient` (Phase 1.2).
- Each request gets its own response context with unique `resp_` IDs. No cross-leaking of state between concurrent requests against the same profile.
- However, concurrent requests to the same profile will share conversation history (if `previous_response_id` or `conversation` is used). This is expected and desirable — each request appends to the same conversation thread.

## Additional observations

### API_SERVER_HOST must be set

The Hermes API server defaults to binding on `127.0.0.1:8642` (loopback only). When running in Docker, this makes the port unreachable from the host even with `-p 8642:8642`. You MUST set `API_SERVER_HOST=0.0.0.0` to make it accessible. This was discovered by checking the container's `/proc/net/tcp` — the bind address was `0100007F:21C2` (127.0.0.1:8642) instead of `00000000:21C2` (0.0.0.0:8642). The env var was found by grepping the Hermes Python source at `/opt/hermes/gateway/config.py` inside the container.

### Dockerfile approach needs adaptation

The plan's Phase 1.1 Dockerfile uses `pip install hermes-agent` which doesn't work — `hermes-agent` is not on PyPI. It installs from GitHub via `pip install git+https://github.com/NousResearch/hermes-agent.git@<tag>`. Our adapted approach uses the official Docker image as a base (`FROM nousresearch/hermes-agent:v2026.4.16`) and adds our extras on top.

### API model distinction

The `/v1/responses` endpoint has two modes:
1. **`model: "hermes-agent"`** — Full agent loop with all tools (terminal, read_file, etc.). Tool calls are executed internally and their results appear as `function_call` + `function_call_output` items in the SSE stream.
2. **`model: "google/gemini-2.5-flash"`** (or any LLM model name) — Raw LLM call without agent tools. The model doesn't have access to Hermes's tool suite and will refuse to call tools.

For our integration, we should always use `model: "hermes-agent"` to get the full agent experience with tool calling.

### SSE event schema (Responses API)

Complete event types observed:

| Event | Description |
|---|---|
| `response.created` | Initial response object with status `in_progress` |
| `response.output_item.added` | New output item starting (function_call, function_call_output, or message) |
| `response.function_call_arguments.delta` | **NOT PRESENT** — arguments arrive atomically in `function_call` item |
| `response.output_text.delta` | Streaming text delta (token-by-token for assistant messages) |
| `response.output_text.done` | Complete text for a message content part |
| `response.output_item.done` | Output item completed (with full content) |
| `response.completed` | Final event with full response object including usage stats |
| `response.failed` | Error event when LLM provider is misconfigured or call fails |

### Data directory

Hermes uses `/opt/data` as the persistent data directory (not `/data` as some docs suggest). Docker volumes should mount to `/opt/data`. The user inside the container is `hermes` (UID 10000).

The 57.59 MiB idle RAM includes all 79 bundled skills (after v0.9.0 update). This is the worst-case idle figure — no conversation active, no model loaded (model runs on OpenRouter, not locally).
