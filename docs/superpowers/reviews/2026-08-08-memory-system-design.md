# Multi-Dimensional Fleet Review — Memory System Design (Spec)

**Spec:** `docs/superpowers/specs/2026-08-08-memory-system-design.md` (2026-08-08, 291 lines, pre-implementation design)
**Review date:** 2026-08-08
**Method:** six parallel read-only subagents, one per dimension — security, architecture, correctness/spec-internal + spec↔parent↔rules consistency, slice-feasibility/executability, testing/e2e, maintainability/operability/config/degradation. Each read the spec plus referenced rules, the parent design (`2026-07-23-sentient-2.0-native-orchestrator-design.md`), the declared precedent (`2026-08-08-skill-system-design.md`), and source for grounding (file:line citations where possible). No agent modified files or git state.
**Relationship to the spec's own scope notes:** the spec carries accepted-gap disclosures (§1 non-goals, §14 open questions); this review evaluates whether the *design* is internally sound, faithful to its parent + the project rules, and safe to plan off — surfacing contradictions, unmechanismed security claims, and spec-silence the design does not self-identify.

## Headline — ten findings reach across dimensions

### 1. The "sources of truth never move / deep-memory is derived and rebuildable" invariant is FALSE for episode-summaries (Architecture MAJOR, corroborated by Correctness MAJOR)

§2 claims "Everything under `deep-memory/` is derived and rebuildable: delete it, `rebuild` regenerates it from sessions + files. No irreplaceable data ever lives in the index." §10 repeats: "rebuild regenerates from sources of truth (session store + files)." But §8's dreamer produces "Episode summaries — one per session → indexed as `episode-summary`" via an LLM call, and §5.4 names `episode-summary` the **"primary signal."** The episode-summary `text` is (a) LLM-generated (non-deterministic), (b) stored ONLY in the index — the session store holds the raw transcript (the `sourceRef` points back to it), and §8 writes the *journal* to a file but says nothing about writing episode-summaries to a file. The `rebuild` endpoint (§5.2) is "drop + await re-upserts (gateway drives re-feeding from sources of truth)" — the service merely re-indexes what it is fed; it does not run LLM calls. Re-feeding file-sections reads files; re-feeding journals reads journal files; but re-feeding episode-summaries requires **re-running the dreamer** (a non-deterministic LLM call). So episode-summary text is canonical-only-in-the-index — a lossy one-way transform — and a `rebuild` LOSES the index's primary signal. The "derived/rebuildable, no irreplaceable data in the index" claim is false for exactly the entry kind that matters most.

**Fix (pick one, state it):** (a) the dreamer writes episode-summaries to a canonical file (e.g. `memory/episodes/<sessionId>.md`) so they are a source of truth and `rebuild` reads them back — cleanest, makes dreamer output durable + auditable alongside the journal; (b) scope the "rebuildable" claim to file-sections + journals only and state episode-summaries require a dreamer re-run (expensive, non-deterministic); (c) `rebuild` explicitly triggers a dreamer re-run for the affected scope.

### 2. Dreamer provenance laundering defeats the §3.1 poison-removal defense on its single highest-risk path (Security HIGH, corroborated by Correctness MAJOR)

§3.1 records provenance (`user-speech | assistant | tool-derived`) on every entry and claims this makes poison "traceable and revocable" via `purge(provenance=…)`. But the dreamer (§8) reads whole sessions — including untrusted `tool_result` text (§3 explicitly flags the dreamer reads "whole sessions — including tool results and delegated-task output, i.e. untrusted text") — distills them through an LLM call, and writes facts. The spec is SILENT on how the dreamer assigns provenance to its OUTPUTS when its inputs are mixed-provenance. If dreamer-distilled facts carry `assistant` provenance (the dreamer is an assistant-side LLM call), then tool-derived poison is laundered to a higher-trust tier and `purge(provenance=tool-derived)` cannot find it — the entire provenance-based purge defense is defeated at exactly the one boundary where untrusted text becomes "memory." This is load-bearing for v1 because the write-time scan is syntactic (see headline #6) and cannot catch semantic laundering.

**Fix:** specify taint propagation — a dreamer-distilled fact's provenance = the **least-trusted** provenance of any input that contributed to it (if the source session contains any `tool-derived` entry, all facts distilled from that session carry `tool-derived`). The §5.4 index schema needs a field recording this (e.g. `inputProvenance`, or the `provenance` field is defined as the min-trust of inputs, not the writer's identity). §8 must state the per-fact provenance assignment policy explicitly.

### 3. The auxiliary seam is the wrong fit for the dreamer's input scale, and the spec is silent on it (Architecture MAJOR, corroborated by Maintainability MAJOR + Correctness MINOR)

§8 says the dreamer uses "the auxiliary seam (`orchestrator.auxiliary`)." The auxiliary seam (`gateway/src/runtime/auxiliary-task.ts:112-125,288`) bounds EVERY substituted variable across ALL auxiliary tasks to a SINGLE shared `input_truncation_chars` (default 4000, `config.yaml:388`), water-filled across variables. The dreamer reads WHOLE SESSIONS ("window: sessions since last dream," §8) — easily 50k+ chars; 4000 chars truncates a session to ~1000 words, losing most of the content the dreamer needs to summarize. The spec says "the dreamer gets its own generous output cap distinct from titling's" but is SILENT on the input budget. The closest precedent — compaction (`compaction.ts:239-252`) — does NOT use the auxiliary seam; it makes its own direct `provider.stream` call with a system message and its own `summarizer_max_output_tokens` budget, precisely because it needs long input the auxiliary seam's shared truncation would destroy. The dreamer is structurally closer to compaction (reads sessions, long input, multi-step) than to titling (one-shot, short input). Compounding it: §8's "own generous output cap" is not in §11's config block — the only `max_output_tokens` is the titling cap (`orchestrator.auxiliary.max_output_tokens: 200`, `config.yaml:383`), which the dreamer cannot reuse.

**Fix (pick one, state it):** (a) the dreamer uses its own direct provider call like compaction (and the spec stops claiming the auxiliary seam), with its own `dreamer.max_input_chars` / `dreamer.max_output_tokens` under `orchestrator.memory.dreamer`; (b) the auxiliary seam grows a per-task input + output budget (new config key per auxiliary task name) so the dreamer can declare larger ones without inflating titling's. Either way, add the dreamer output cap to §11.

### 4. Spark scoring math is self-defeating — "strong old memories" can never fire (Correctness MAJOR)

§6 states the design intent: decay has a floor "so an old-but-strongly-relevant memory (the childhood story, last year's Tahoe trip) can still fire." §11 sets `recency_floor: 0.35` and `min_score: 0.55`. The formula (§6) is `score = relevance × decay(age)`, with `relevance` normalized 0–1 and `decay` floored at 0.35. For an old memory (decay at floor), the maximum possible score is `1.0 × 0.35 = 0.35`, which is below `min_score: 0.55` → the memory is blocked. Even at one half-life (90 days), `decay = 0.5`, so `1.0 × 0.5 = 0.5 < 0.55` → still blocked. For the floor to achieve its stated purpose, `recency_floor` must be ≥ `min_score`. As written, no memory older than ~60 days can ever spark regardless of relevance — directly contradicting §6's explicit claim and §1's "past conversations can spark back" goal. This is a numbers problem, not a design flaw.

**Fix:** raise `recency_floor` to ≥ 0.55, lower `min_score` to ≤ 0.35, or redefine the floor to apply to the composite score so the floor and threshold are consistent.

### 5. `orchestrator.memory` config block has no stated default — bricks every operator on upgrade (Maintainability CRITICAL)

§11 proposes adding `orchestrator.memory` to `orchestratorConfigSchema` but never states the block is `.default({})` / optional. The existing schema (`shared/config/src/schemas/orchestrator-config.ts:46-58, 82-98, 137-188, 189-231`) gives EVERY nested sub-block (permission, skills, auxiliary, compaction) a `.default({})` with the explicit comment "operator configs are edited in place and predate this key — a missing block must never brick boot for a gateway that was working yesterday." An operator who HAS `orchestrator:` present (the production config at `gateway/config.yaml:227`) but lacks `memory:` inside it will fail zod parse if `memory` is a required field with no default. This is the exact defect the skill-system review caught: a new config section without a default bricks every operator on upgrade.

**Fix:** add to §11: "The `memory` block defaults to `{}` — an operator config predating this key keeps booting; every leaf field carries its own zod default so a partial block is valid." Mirror the `.default({})` comment pattern from `orchestrator-config.ts:55-58, 95-98, 185-188`.

### 6. No timeouts on the per-turn spark search or the deep-memory service HTTP calls (Maintainability HIGH x2, error-handling rule violation)

§6 runs a service `search` call on EVERY conversational turn; §5.2 lists five HTTP endpoints the gateway client dials. §10 covers "service down" but not "service slow." §11 has no `spark.timeout_ms` and no `deep_memory.request_timeout_ms`. The error-handling rule (`error-handling.md:8`) mandates "Timeout every external call. No unbounded waits." A slow-but-alive deep-memory service with no per-turn deadline adds unbounded latency to the hot path of **every conversation**; the dreamer's bulk upsert calls (§8, indexing episode summaries + journal + facts for every session) are an unbounded call on the nightly job.

**Fix:** add `spark.timeout_ms` (e.g. `z.number().int().min(50).max(5000).default(500)`) and `deep_memory.request_timeout_ms` to §11; state in §6/§10 that the spark search is deadline-bounded (on expiry, spark withheld with a WARN — the existing "silently absent" path) and every service HTTP call is deadline-bounded (on expiry, typed error: upsert → dreamer logs + skips that entry; search → spark/recall degrades per the existing paths).

### 7. Purge cascade is claimed but has no mechanism, AND purge ships only in S4 — S1–S3 have no poison-removal path (Security HIGH + Slice BLOCKER)

§3.1 says `purge(provenance=…, sourceRef=…)` "removes it and everything derived from it." The §5.2 API is `{indexPath, sourceRef?, provenance?}` — a flat filter with no cascade parameter. The §5.4 index schema has NO `derivedFrom` or derivation-chain field. The derivation chain is: raw session → episode-summary (`sourceRef={sessionId, entryRange}`) → journal (`sourceRef={file, heading}`) → MEMORY.md facts (`sourceRef={file, heading}`). A `purge(sourceRef={sessionId: X})` catches episode-summaries for session X but NOT journals or MEMORY.md facts derived from those summaries — their `sourceRef` points at files, not the session. There is no mechanism to traverse the derivation graph. Compounding it: §13 S4 names "purge/rebuild operator paths," so the security-critical poison-removal capability the §3 model depends on does not exist in S1–S3. A poisoned memory written in S1–S3 is stuck until S4 ships; the §3 security model is incomplete for the first three slices.

**Fix:** (a) add a `derivedFrom: entryId[]` field to the schema + have purge traverse it recursively, OR define a cascade implementation that re-runs the dreamer's derivation map (which must be stored); (b) move `POST /purge` + a minimal operator endpoint into S2 (the service exists then), with the operator CLI/endpoint as the S4 "operator paths" hardening, OR explicitly state in §10 that S1–S3 remediation is "operator deletes the markdown file + index rebuild" and name the residual risk.

### 8. Cross-user isolation has no service-level backstop — the first multi-user capability service trusts the gateway exclusively (Security HIGH)

§3.4: "the gateway resolves capabilities to index paths; the service never sees a search-everything request." §5.1: the service "refuses any path outside its configured data root." But the data root is shared across ALL users and scopes (`~/.sentient/gateway/` covering `users/<A>/deep-memory/`, `users/<B>/deep-memory/`, `shared/family/deep-memory/`). The service "knows nothing about users, sessions, or scopes" and authenticates only via a shared gateway token (§3.7) — not per-user. So cross-user isolation depends ENTIRELY on the gateway's capability→indexPath resolution with zero service-level backstop. §3.7's "same trust shape as whisper-stt/local-tts" is inaccurate — STT/TTS are single-stream services with no cross-user data and no auth token (`capabilityServices/LocalTTSService/CONTRACT.md:21`); deep-memory is the first multi-user capability service with a shared data root. The parent spec (§2.5) establishes "code-enforced capabilities are the boundary; OS-level physical separation is a free second layer" — here the code boundary is ONLY at the gateway and the second layer is absent. A gateway bug (or any direct service call) could send user B's indexPath on user A's request and the service cannot detect it. §3.9's test claims "user A cannot read/search/write user B's memory by any path" but does not include the forged-indexPath-at-the-service case.

**Fix:** the service must validate per-request that each requested indexPath is within a caller-scoped allowlist: (a) per-user auth tokens (not a shared gateway token), or (b) the gateway passes a set of allowed indexPaths alongside the request and the service verifies the requested indexPath is in that set, or (c) the service resolves indexPaths from a per-request scope token, never accepting raw paths. At minimum, the §3.9 isolation test MUST include a service-level indexPath-forgery case.

### 9. Slices S2 and S3 are each too large for one subagent wave, and the matrix row→slice mapping is absent (Slice BLOCKER + MAJOR x2)

§13 line 281 says "the e2e matrix rows activate per slice" without giving the mapping. The `spark-happy` row's pre-state is "indexed Tahoe episode," but episode-summaries (the primary signal, §5.4) are written ONLY by the dreamer (S3), while S2 ships spark indexing only file-section entries ("indexing of file writes"). So `spark-happy` is unreachable in S2 — S2 cannot claim green on it, yet S2 is the slice that ships spark. The spec does not acknowledge that S2 spark is missing its strongest signal. Separately, S2 (Python+MLX service + venv + orchestrator registration + gateway client + indexing + spark + real recall) and S3 (nightly scheduler + catch-up + episode summaries + journal + fact reconciliation + op application + preservation rail + archive + indexing) are each larger than the entire skill-system precedent plan (~13 tasks / 4 waves for a TS-only feature with no new runtime). A single subagent wave each risks the context-overflow failure the precedent review already flagged.

**Fix:** add an explicit row→slice mapping table (split `spark-happy` into `spark-file-happy` S2 + `spark-episode-happy` S3, or move it to S3 and add a file-only S2 spark case); split S2 into **S2a** (service skeleton + health + client + orchestrator registration + wire-contract test) and **S2b** (indexing + spark + real recall); split S3 into **S3a** (nightly scheduler + catch-up + episode summaries + journal + indexing — "read sessions, write episodic records, never touch MEMORY.md") and **S3b** (fact reconciliation + op application + preservation rail + archive — the sole writer of distilled memory and the highest injection risk, gated separately).

### 10. The e2e matrix does not meet the e2e rule: 5 of 9 §3 defenses untested, aspirational log trails, no @live dreamer smoke, hand-wavy mobile (Testing MAJOR x7)

- **5 of 9 §3 security defenses have no test in §12.** §3 lists 9 structural defenses; §12 tests only write-time scan (3.2), gate annotation (3.3 — named, no dedicated row), cross-scope (3.4/3.9). UNTESTED: provenance recording (3.1), `memory` ResourceClass wrong-class rejection (3.5 — the spec itself flags this as the confused-deputy lesson), supersede-never-delete (3.6), service boundary confinement (3.7), no-content-in-logs (3.8 — `testing.md:9` explicitly lists "log sanitization" as a security boundary). A defense untested is a defense that silently regresses.
- **No `@live` dreamer smoke — the one surface where @live gating matters most.** The dreamer makes real paid LLM calls via the auxiliary seam (same provider as the main loop). §12's only `@live` flow is the free local DeepMemoryService. The dreamer is the riskiest component (reads untrusted text → LLM → distilled memory → every future session's system prompt). A mocked LLM cannot validate extraction quality, the preservation rail against a real hallucinating model, or the scan against real hostile content. The e2e rule permits paid services "if the feature specifically depends on them" — the dreamer's core behavior does.
- **Every matrix log trail is aspirational, not a concrete greppable contract.** Each row's "Expected log trail" is prose ("memory_write PDP allow, scan pass, cap usage logged"), not a pinned event name. The project norm (skill-tools `skill-tools.write.ok`/`skill-tools.scan.rejected` at `gateway/src/tools/skill-tools.ts:138,221`; `inbound-gate.flagged` at `inbound-gate.ts:108`) pins exact events. A case cannot be objectively green against a description.
- **No reusable cases added to `agents/docs/testing-knowledge.md`.** §12 defines all 12 cases inline and names no short-name references; `cross-user-isolation` duplicates `cross-user-refused` (testing-knowledge:569). The rule says new reusable cases go there.
- **Mobile Maestro tagging is hand-wavy.** §12 says "tag memory cases into existing Maestro flows… no new native driver work expected." Verified: `qa/mobile/flows/` has chat flows tagged `chat` that exercise send/receive/interrupt, NOT memory tools; none prompt memory use. "No new native driver work expected" is false — new prompt-driven flows are needed, or an honest deferral.
- **Viewport matrix under-covered.** 11 of 12 rows are 1280×900; only `mobile-spark` is 390×844. `e2e-testing-details.md:48`: "Run every case at both viewports unless the feature is desktop-only or mobile-only." Memory is chat-driven — user-visible at mobile viewport.
- **`dream-run` is an integration test mislabeled as e2e.** Its Viewport is "n/a (log-driven)", no browser interaction, no user-visible browser behavior — it's an FSM/integration test. The e2e-relevant dreamer assertion is its *downstream* effect: after a dream, a NEW session reflects distilled memory.

**Fix:** add a security-boundary test per §3 defense; add a gated `@live` dreamer smoke; pin concrete log event names per row (`memory-tools.write.ok`, `memory-retriever.spark.hit | score=…`, `memory-recall.unavailable | reason=…`); commit durable rows to `testing-knowledge.md` under a `memory` surface tag (reference `cross-user-refused` instead of duplicating); author memory-prompting Maestro flows or explicitly defer native-mobile parity with the real reason; add a 390×844 leg to chat-driven rows; move `dream-run` to the FSM doctrine list, replace with `dream-reflects-next-session`.

4. **[HIGH, Security + Slice] Purge cascade unmechanismed AND deferred to S4.** `purge(provenance=…, sourceRef=…)` claims "removes it and everything derived" but the schema has no `derivedFrom` field + the API is a flat filter; derivation crosses `sourceRef` shapes so cascade can't traverse. AND the security-critical poison-removal path doesn't exist until S4, leaving S1–S3 with no remediation. Fix: add `derivedFrom` + recursive purge (or a stored derivation map); move `POST /purge` + a minimal operator endpoint into S2 (service exists then), or explicitly accept S1–S3 remediation is manual file deletion + index rebuild with the residual risk named.

5. **[HIGH, Security] Cross-user indexPath forgery — no service-level backstop for the first multi-user service.** The shared token authenticates the gateway, not the user; the service data root is shared across all users/scopes; isolation depends entirely on gateway capability resolution with zero service backstop. Fix: per-request scope validation at the service (per-user tokens, or gateway passes an allowed-indexPath set the service verifies, or service resolves from a scope token); add a forged-indexPath case to §3.9.

6. **[MAJOR, Correctness] Spark scoring math is self-defeating.** `recency_floor: 0.35 < min_score: 0.55` means no memory older than ~60d can ever spark regardless of relevance — contradicts §6's "strong old memories still fire" + §1's spark goal. Pure numbers fix: make the two thresholds consistent.

7. **[HIGH, Maintainability] Missing timeouts on the per-turn spark + service HTTP calls.** No `spark.timeout_ms` (per-turn hot path can hang every conversation) + no `deep_memory.request_timeout_ms` (dreamer bulk upsert unbounded). Violates `error-handling.md:8`. Fix: add both to §11 + state the deadline-bounded behavior in §6/§10.

8. **[BLOCKER, Slice + Correctness] Slices S2/S3 too large + no row→slice mapping + `spark-happy` pre-state unreachable in S2.** S2 (new Python runtime + full spark/recall) + S3 (5+ dreamer sub-components incl the safety-critical rail) are each larger than the entire skill-system precedent plan; a single subagent wave each risks context-overflow. `spark-happy`'s "indexed Tahoe episode" pre-state can't be satisfied in S2 (episode-summaries are S3). Fix: add explicit row→slice mapping; split S2→S2a/S2b, S3→S3a/S3b (isolating the preservation rail in S3b); split `spark-happy` into file-only S2 + episode-summary S3.

9. **[MAJOR x7, Testing] The e2e matrix does not meet the e2e rule.** 5 of 9 §3 defenses untested (incl the two the spec flags as lessons); no `@live` dreamer smoke (the paid-LLM riskiest component); aspirational log trails not greppable events; no reusable cases added to testing-knowledge; hand-wavy mobile Maestro tagging; viewport under-covered; `dream-run` mislabeled as e2e. Fix: pin concrete log event names per row; add the 5 missing §3 defense tests; add a gated `@live` dreamer smoke; commit durable rows to testing-knowledge under a `memory` surface tag; author memory-prompting Maestro flows or honestly defer; add 390×844 legs; move `dream-run` to FSM doctrine, add `dream-reflects-next-session`.

10. **[MAJOR, Slice + Correctness] Cache-stability invariant (§4.5) not pinned + S1 stub contract undefined.** No matrix row pins the two-sided mid-session→next-session invariant; the S1 `memory_recall` stub return value is unspecified. Fix: add `memory-cache-stability` row; define the stub returns the typed `deep_memory_unavailable` error (so `recall-degraded` activates in S1).

**Net assessment:** the design's bones are strong — faithful reuse of two proven seams (skill-system per-user-state + native-tools + prompt-rendering pattern; system-orchestrator native-addon supervision), clean composition into the existing per-session/per-turn prompt cascade without new ReAct hooks, a structurally sound security model that correctly inherits the write-time fail-closed + ResourceClass-before-path-check lessons. The slice-sizing + testing gaps (#8/#9) are execution-readiness issues that must be resolved before a plan is authored off this spec. With the ten must-fix items addressed, the spec is sound to plan and execute against.
