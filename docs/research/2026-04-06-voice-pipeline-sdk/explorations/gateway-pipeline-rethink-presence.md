# Rethink: Gateway Pipeline — Presence Gap Analysis

## Methodology

Traced every moment from user action to system response in the gateway pipeline, comparing:
1. **Current production code** — what actually gets sent to the client today
2. **PoC state machine** — what the formal model emits
3. **Ideal experience** — "never break immersion" principle

## Timeline Trace: Full Turn Lifecycle

### Phase 1: Session Start → Ready

```
User action: opens voice mode / presses connect
─────────────────────────────────────────────────────
T0   WS connection established
T1   Auth token verified
T2   STT provider connecting...          ← SILENT GAP (production)
T3   TTS provider connecting...          ← SILENT GAP (production)
T4   Both providers ready
```

**Production gap:** `voice-handlers.ts:handleVoiceStart()` calls `startRecording()` which initiates STT connection, but the client receives no feedback until audio.start is acknowledged. If Deepgram takes 500ms+ to connect, the user stares at nothing.

**PoC state machine:** Emits `SEND_STATUS: "connecting"` on SESSION_START → `SEND_STATUS: "ready"` on PROVIDERS_READY. Gap covered.

**Proposed indicators:**
- `status.connecting` — immediately on WS auth success
- `status.ready` — when providers are connected

### Phase 2: Utterance Start → Audio Streaming

```
User action: starts speaking (VAD triggers or button press)
─────────────────────────────────────────────────────
T5   utterance.start received
T6   Audio chunks flowing to STT
T7   STT emits partial transcripts       ← DISCARDED (production)
T8   More audio chunks...
```

**Production gap:** `voice-session.ts:131-138` — `readNextFinalTranscript()` filters for `isFinal: true` only. Partial transcripts are generated by Deepgram (`interim_results: "true"` is configured) but **never relayed to the client**. The `transcript.partial` message type exists in `shared/protocol/src/messages.ts` but is never sent. During this phase the user has no confirmation their speech is being recognized.

**PoC state machine:** Emits `RELAY_PARTIAL_TRANSCRIPT` on every `TRANSCRIPT_PARTIAL` event during both `receiving-audio` and `finalizing-stt`. Gap covered.

**Proposed indicators:**
- `status.listening` — on utterance.start
- `transcript.partial` — relay Deepgram partials as they arrive (message type already defined)

### Phase 3: Utterance End → Final Transcript

```
User action: stops speaking (VAD triggers or button release)
─────────────────────────────────────────────────────
T9    utterance.end received
T10   STT finalize() called
T11   ...waiting for isFinal transcript   ← SILENT GAP (production, no timeout!)
T12   Final transcript arrives
```

**Production gap (CRITICAL):** `readTranscriptOrNull()` in `voice-handlers.ts` awaits the final transcript **with no timeout**. If STT never returns a final event (Deepgram connection stall, network issue), the pipeline hangs forever. The user sees nothing — no "processing" indicator, no timeout message.

**PoC state machine:** `finalizing-stt` state has a 5-second timeout guard. Emits `SEND_STATUS: "processing"` on entry. On `STT_TIMEOUT`, transitions to error with `SEND_ERROR`. Gap covered.

**Proposed indicators:**
- `status.processing` — immediately on utterance.end (before transcript arrives)
- `status.error: "I didn't catch that"` — after 5s STT timeout

### Phase 4: Transcript → LLM Response Start

```
─────────────────────────────────────────────────────
T12   Final transcript received
T13   ContextAssembler.buildMessages()
T14   llmProvider.stream() called
T15   ...waiting for first LLM token      ← SILENT GAP (production)
T16   First token arrives
```

**Production gap:** Between receiving the transcript and the first LLM token, there is no indicator. `runVoiceTurn()` in `voice-turn.ts` starts the LLM stream and creates the StreamingOverlap, but no "thinking" indicator is sent until `text.delta` events start flowing. Time to first token can be 500ms–3s depending on model and prompt length.

**PoC state machine:** Emits `SEND_STATUS: "thinking"` immediately on entering `running-llm`. Has a 30-second timeout guard. Gap covered.

**Proposed indicators:**
- `status.thinking` — immediately when LLM stream starts (before first token)
- `status.error: "Sorry, taking too long"` — after 30s LLM timeout

### Phase 5: LLM Tokens → First Audio

```
─────────────────────────────────────────────────────
T16   First LLM token
T17   More tokens... text.delta sent
T18   SentenceAggregator detects boundary
T19   First complete sentence
T20   TTSProvider.synthesize() called
T21   ...waiting for first TTS audio chunk  ← SUBTLE GAP
T22   First audio chunk arrives
T23   audio.start sent to client
```

**Production gap (subtle):** Between the first `text.delta` and the first `audio.frame`, there's a period where the user sees text appearing but hears nothing. This is actually fine UX — text is the indicator. However, if the LLM produces a very short response (1-2 words) that doesn't trigger a sentence boundary, the SentenceAggregator's 2-second flush timer kicks in. The user sees a couple of words, then waits 2 seconds in silence before audio starts.

**PoC state machine:** Emits `SEND_STATUS: "speaking"` on first SENTENCE_READY. The gap between text.delta and audio is covered by text itself.

**Proposed indicators:**
- `text.delta` events already serve as presence (keep as-is)
- `status.speaking` — when first audio frame is about to be sent
- Consider: reduce sentence aggregator flush timeout from 2s → 1s for short responses

### Phase 6: Audio Streaming → Turn Complete

```
─────────────────────────────────────────────────────
T23   audio.start → audio.frame... → audio.frame
T24   LLM stream may complete (LLM_DONE) while TTS still active
T25   Last TTS audio chunk
T26   audio.done sent                     ← GAP: no "ready" indicator
T27   ...user doesn't know they can speak again
```

**Production gap:** After `audio.done`, the client receives no explicit "ready for your next utterance" signal. The `voice-handlers.ts:handleVoiceEnd()` pushes history and returns, but never sends a status message. The client must infer readiness from audio completion.

**PoC state machine:** Emits `SEND_STATUS: "ready"` on TURN_COMPLETE transition to idle. Gap covered.

**Proposed indicators:**
- `status.ready` — explicitly sent after audio.done + history appended

### Phase 7: Barge-In

```
User action: speaks during assistant response
─────────────────────────────────────────────────────
T28   barge_in received
T29   AbortController.abort()
T30   ...stages cleaning up               ← BRIEF GAP (production)
T31   Audio stops, new utterance begins
```

**Production gap (minor):** `voiceSession.bargeIn()` aborts the signal, which causes generators to terminate. The client stops receiving audio. But there's no explicit acknowledgment that barge-in was received — the client infers it from audio stopping. If abort propagation takes time (TTS connection cleanup), there could be a brief stutter.

**PoC state machine:** Goes through `cancelling` state with `ABORT_TURN` effect, then `CANCEL_COMPLETE` → idle with `SEND_STATUS: "ready"`. Explicit cancellation acknowledgment.

**Proposed indicators:**
- `barge_in.ack` — immediate acknowledgment when barge-in received
- `status.listening` — once cancellation complete and new utterance begins

### Phase 8: Provider Drops

```
Provider connection drops mid-operation
─────────────────────────────────────────────────────
T?    STT WebSocket closes unexpectedly
T?    ...pipeline hangs on next read       ← SILENT GAP (production)
```

**Production gap (CRITICAL):** If the STT WebSocket drops during `receiving-audio`, `voice-session.ts` has no detection mechanism. The `transcripts()` async generator will either hang forever or throw. If TTS drops during `streaming-response`, the `synthesize()` generator throws, but the error propagation is indirect (captured in variable, surfaced late per `streaming-overlap.ts`).

No reconnection logic exists. No user-visible error message for provider drops.

**PoC state machine:** PROVIDER_DROPPED event triggers `reconnecting` state with `SEND_STATUS: "reconnecting"`, 3 retries, 10s timeout. Falls back to `error` state with `SEND_ERROR` if retries exhausted.

**Proposed indicators:**
- `status.reconnecting` — when provider drop detected
- `status.error: "Connection interrupted, reconnecting..."` — if retries in progress
- `status.error: "Connection lost. Please try again."` — if retries exhausted

### Phase 9: Empty Transcript

```
─────────────────────────────────────────────────────
T12   Final transcript arrives — but it's empty (silence, noise)
T13   ...pipeline continues with empty string? ← UNDEFINED BEHAVIOR
```

**Production gap:** `readTranscriptOrNull()` returns `null` if no transcript found, and `handleVoiceEnd()` checks this and returns early. But the client receives NO feedback — no "I didn't hear anything" message, no status change. The user doesn't know if the system is broken or just didn't hear them.

**PoC state machine:** Doesn't explicitly model empty transcripts as a distinct case. This is a gap in both.

**Proposed indicators:**
- `status.empty_utterance: "I didn't catch that, could you try again?"` — when transcript is empty/null
- Return to `status.ready` immediately after

### Phase 10: Double Utterance

```
User speaks again before first response completes
─────────────────────────────────────────────────────
T14   First utterance still in LLM stage
T15   utterance.start for second utterance arrives
T16   ...what happens?                     ← UNDEFINED (production)
```

**Production gap:** The current code processes audio.start/audio.end sequentially in `handleVoiceEnd()`. If a second audio.start arrives while the first turn is still running, it calls `startRecording()` on the same session. The behavior is undefined — could corrupt the STT stream or silently drop the second utterance.

**PoC state machine:** Handles UTTERANCE_START during `running-llm` and `streaming-response` by first triggering barge-in (abort current turn), then starting new utterance. The transition is explicitly modeled.

**Proposed indicators:**
- Implicit barge-in + `status.listening` — treat as barge-in, then listen

## Summary: Gap Inventory

| # | Gap | Severity | Production Status | PoC Covers? |
|---|-----|----------|------------------|-------------|
| 1 | Provider connecting — no feedback | Medium | Silent | Yes (connecting/ready) |
| 2 | Partial transcripts discarded | High | transcript.partial defined but unused | Yes (RELAY_PARTIAL_TRANSCRIPT) |
| 3 | STT finalization — no timeout, no indicator | Critical | Can hang forever | Yes (5s timeout + processing status) |
| 4 | LLM thinking — no indicator before first token | High | Silent 500ms–3s | Yes (thinking status + 30s timeout) |
| 5 | Short response aggregator delay | Low | 2s silence | Partially (text.delta covers) |
| 6 | Post-audio — no "ready" signal | Medium | Client must infer | Yes (ready status) |
| 7 | Barge-in — no acknowledgment | Low | Client infers from audio stop | Yes (cancelling state) |
| 8 | Provider drop — no detection/recovery | Critical | Hangs or throws | Yes (reconnecting + retries) |
| 9 | Empty transcript — no feedback | Medium | Silent return | No — gap in both |
| 10 | Double utterance — undefined behavior | High | Undefined | Yes (implicit barge-in) |

## Proposed Indicator State Map

Complete set of user-facing status indicators the gateway should emit:

```
status.connecting     "Setting up..."          Session start → providers connecting
status.ready          "Ready"                  Providers connected / turn complete / recovery
status.listening      "Listening..."           utterance.start received
status.processing     "Processing..."          utterance.end, waiting for STT final
status.thinking       "Thinking..."            LLM stream started, before first token
status.speaking       "Speaking..."            First audio frame being sent
status.reconnecting   "Reconnecting..."        Provider dropped, retrying
status.error          <user-friendly message>  Timeout, failure, empty transcript
```

These map 1:1 to the SEND_STATUS effects in the PoC state machine, with the addition of `status.error` for empty transcripts (gap #9).

## Recommendations

1. **Add empty transcript handling** — both to the PoC state machine (new event `TRANSCRIPT_EMPTY`) and exploration. User should get "I didn't catch that" not silence.

2. **Relay partial transcripts** — the infrastructure exists (`transcript.partial` message type, Deepgram `interim_results`). Just wire `voice-session.ts` to emit them instead of filtering.

3. **Add STT finalization timeout** — currently can hang forever. A 5s guard with user-visible "processing" status is critical.

4. **Emit "thinking" before LLM** — a single status message between transcript arrival and first token eliminates the most noticeable gap.

5. **Emit "ready" after turn** — explicit signal lets client re-enable mic indicator.

6. **Barge-in acknowledgment** — minor but reduces perceived latency.

7. **Provider drop detection + reconnection** — critical for continuous mode where STT stays connected across utterances.

8. **Reduce aggregator flush timeout** — 2s → 1s for short responses to reduce audio start delay.

## Assessment

The PoC state machine already covers 9 of 10 identified gaps through its SEND_STATUS effect system. The one missing gap (empty transcript) is a minor addition. The production code has **zero** of these indicators — every transition is silent except for the data itself (text.delta, audio.frame).

The primary implementation task is wiring the FlowManager to emit these status messages at each state transition, which the PoC's effect-based architecture makes mechanical: each SEND_STATUS effect in the transition table becomes a WS message send.
